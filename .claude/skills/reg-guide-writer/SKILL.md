# reg-guide-writer — 規制の徹底解説ページを書く（2026-10-11 darari「スキルにしておこう」）

このサイトの徹底解説は**正確さが命**で、そのうえで**わかりやすい文章**であること（darari 2026-10-11「もうちょっとわかりやすい文章がいい」）。
1ページを「計画 → 執筆（Opus）→ 照合（Fable）→ 直し → 公開」で回す。kaishu-fable-flow の型をこのページづくりに合わせたもの。

## 0. 先に決めること（本体が書く計画書）

計画書は scratchpad に `plan_<guide-id>.md` で置く。手本: EU の子ページの計画書（下の「手本」）。書くこと:

1. **置き場所と親子**: 本体（全体像）か子ページ（1テーマを深く）か。1ページに足しすぎない。章が増えて読みにくくなるなら子ページに分け、本体は要点＋「詳しくは →」にする（darari「どんどん増えていくので全体のバランスを見ながら」）。
2. **読者**: 日本企業でAIを導入・開発する人（情シス・法務・企画・開発）。誰が読んで、読んだ後に何ができるようになるか。
3. **章立て**: 0章「このページの使い方」で始め、最後は「よくある質問」「出典一覧」。具体例の章と「日本企業の場面別」の章を入れる。
4. **一次資料**: 条文の全文（取得元と保存先）、当局の公式ページ、ガイドライン。法律事務所の記事は補助だけ。
5. **検査内容**（下の 4）。

## 1. 正確さの決まり（執筆者に必ず渡す）

- 条文番号・号・日付・金額・閾値・期限は、**一次資料を実際に開いて確認できたものだけ**書く。記憶で書かない。確認できないことは書かないか「未確認」と書く。
- 改正がある法律は**改正後の文言**で書く（EU AI法は改正規則 (EU) 2026/1744 で多くの条が変わった）。改正前と後が違う箇所は対照表にする。
- ガイドライン・Q&A・行動規範は**法的拘束力がない／任意**と明記し、条文の確定解釈のように書かない。例には段落番号を付ける。
- 「当たりうる例／当たらない例」は断定しない（「〜の場合があります」「〜とガイドラインは示しています」）。
- 自分で作った例は1つの架空の会社にまとめ、`example` ブロックで「架空の例」と表示する。条文が求めないことを義務のように書かない。
- 各段落・表の行・FAQ に出典（`sources`）を付ける。validate は出典なし・公式ドメイン以外を弾く（`scripts/validate.mjs` の guides 検査）。
- ページの冒頭と末尾に「法的助言ではありません。最終判断は専門家へ」。
- 執筆者は**事実確認表**（主張 → 出典 → 出典で確認した一文）と「確認できず書かなかったこと」を scratchpad に残す。

## 2. わかりやすさの決まり（執筆時と書き直し時）

業務文書なので `yomiyasu`（business）の考え方に沿う。だらリーヌさんの声では書かない（中立の解説文）。加えて:

- **結論を先に書く**。各章の最初の1〜2文で「つまり何か」を言い切り、条件や例外は後に回す。
- **1文は40字前後、60字を超えたら分ける**。読点は1文に2つまで。
- **条文番号は文の途中に挟まず、文末の括弧にまとめる**（×「第26条1項に基づき導入者は…」→ ○「導入者は…（第26条1項）」）。
- **専門用語は初めて出たところで一言説明する**（例:「導入者（AIを業務で使う会社）」）。同じものを別の言葉で呼ばない。
- **1段落は3文まで**。箇条書きの各項目は1文。
- 漢語の連続を開く（×「適合性評価実施後」→ ○「適合性評価をしたあと」）。「〜しうる」「〜に係る」「〜の観点から」を避ける。
- 読者がやることは「〜してください」ではなく「〜します／〜が必要です」で、義務と任意を言葉で区別する（義務＝「必要です」、推奨＝「〜するとよいでしょう」）。
- 表は「見出しだけ読んでも分かる」短い言葉にする。
- 書き直しのときは**意味（条文・日付・数値・条件・例外）を1つも変えない**。迷ったら元の文を残す。

## 3. 実装の形（既存の作りに合わせる）

- データ: `data/guides/<guide-id>.json`（`schema/guide.schema.json`）。子ページは `parent`、本体は `children` に追加し、関係する章に `links` ブロック（「詳しくは →」）を置く。
- ページ: `src/pages/<親>/<子>.astro`（既存の `src/pages/eu-ai-act/*.astro` と同じ数行の作り。描画は `GuideArticle`・`GuideBlock`）。
- 使えるブロック: p・list・table・note・example（架空の例）・flow（手順）・links・diagram（コードで描いた図。`src/components/diagrams/`、id は schema の enum）・schedule。
- 図が欲しいときは**画像生成でなくコードで描く**（文字が正確・ライト/ダーク・スマホで崩れない・あとで直せる）。デザイン案は Codex の Product Design（`codex-product-design`）に出させてよい。図の中の事実は本文と同じものだけ。
- 実装担当は worktree で作業し、`src/components` の既存部品は作り替えない（図は別作業）。node_modules が無ければ本体のものを一時的にリンクし、終わったら外す。

## 4. 検査（毎回これだけはやる）

A. `npm test`・`DRY_RUN=1 node scripts/validate.mjs`・`ASTRO_BASE=/ npx astro build`
B. スクショ（デスクトップと 375px。375px で横スクロールなし）を `scratchpad/shots/`
C. 事実確認表と「確認できず書かなかったこと」
D. マージ・push・デプロイは本体だけが行う

## 5. Fable の照合（監査）

`Agent`（`model: "fable"`・`subagent_type: "Plan"`・読み取り専用）に渡すもの: worktree とコミット、計画書、事実確認表、一次資料の全文テキストの場所、スクショ。見てもらうこと:

1. 事実確認（条文・日付・数値・例外・ガイドラインの段落番号を原文と照合。改正後の文言か）
2. 誤導（断定・単純化で意味が変わっていないか、架空の例の扱い）
3. わかりやすさの決まり（2）を守っているか（書き直しのときは「意味が変わった箇所」を全部挙げてもらう）
4. 本体との衝突・既存ページへの副作用
5. 判定（反映してよい／直してから／やめる）

指摘は軽いものも全部直してから出す。設計に関わる指摘なら再監査。
